# Архитектура AVGALAXY

## 1. Контур системы

```text
Источники: IFC5, PDF, XLSX, нормативные документы, ArchiMate
        ↓
Ingest и нормализация
        ↓
AVIFC / граф аватара
        ↓
Snapshot
        ↓
Параллельные проверки и обогащение
        ↓
Findings / Diagnostics / Treatment Proposals
        ↓
Решение человека
        ↓
Новое поколение аватара
```

## 2. Основные подсистемы

| Подсистема | Назначение |
|---|---|
| Ingest | Приём IFC5, документов и нормативных источников |
| Normalizer | Приведение данных к AV-модели, контроль единиц и идентификаторов |
| Avatar Core | Графовая БД, AVIFC, служебные файлы |
| Snapshot Service | Создание и фиксация снимков состояния |
| Enrichment | Обогащение, каскады, производные статусы |
| Validation Engine | Применение правил и формирование findings |
| Knowledge Registry | Реестр AVSPUTNIK, правил, источников и версий |
| Decision Service | Фиксация решений и утверждений |
| Storage Service | Raw, snapshots, overlays, AVIFC-версии |

## 3. Ядра brAVium

- `brAVium.pla.pub` — публичный контур планеты: общие знания, опубликованные правила, общие модели.
- `brAVium.pla.loc` — локальный контур: рабочий аватар, приватные данные, локальные проверки.

Физическое объединение хранилищ не требуется. Взаимодействие определяется контрактами и версионированными ссылками.

## 4. ZERO-BUS

ZERO-BUS — инвариант системы: исходные данные не перезаписываются. Все производные значения живут в обогащённых слоях и ссылаются на исходный snapshot.

## 5. Поток проверки

1. Фиксируется snapshot.
2. Подключаются версии AVSPUTNIK.
3. Правила применяются к snapshot.
4. Результаты пишутся в enriched overlay.
5. Формируется diagnosis map.
6. Человек принимает решение.
7. Изменение создаёт новое поколение.

## 6. Границы

Система не требует единой физической базы данных. Графовая БД, AVIFC и служебные файлы могут находиться в одном контейнере аватара или быть распределёнными при сохранении ссылок и версий.
